# 隔空传送公网直连慢速排查报告

日期：2026-10-23（Asia/Shanghai）  
范围：先完成 2.5.2 发布，再分析用户截图中的「猪鸭拆迁队 → Mac」慢速传送；本报告不修改传输代码。

## 结论

**已确认这两次慢速传送是公网直连、没有经过 TURN 中转，且实际速度确实只有约 160 KiB/s。它们没有使用 2.5.1 新增的局域网 TCP 快速通道，而是沿用公网 WebRTC 数据通道。**

目前定位到了实际传输路径，并排除了「把中转误显示成直连」「仅仅是界面瞬时速度显示不准」这两种解释。**还不能根据现有日志断定 160 KiB/s 最终由哪一项造成**：发送端上行/网络整形、UDP 丢包或抖动、SCTP 拥塞与重传、发送端读盘或负载，都需要进一步测量。

因此不能把「公网仍用 SCTP」直接当成全部根因，也不能仅凭直连状态承诺跑满宽带。

## 1. 这次传送的证据

证据来自本机后台日志 `~/Library/Logs/PasteFerry/daemon.log` 与只读查询本机 `pasteferry.db`。没有读取文件内容，也没有向公网对端发送测试文件。

| 接收开始（10 月 22 日） | 完成时间 | 原始文件大小 | 耗时（日志） | 全程平均接收速度 |
| --- | --- | ---: | ---: | ---: |
| 23:12:55.838 | 23:13:32.674 | 6,174,166 B | 36.836 s | 约 164 KiB/s（1.34 Mbit/s） |
| 23:14:42.456 | 23:15:06.747 | 3,959,066 B | 24.291 s | 约 159 KiB/s（1.30 Mbit/s） |

第二行大小约 3.8 MiB，与截图中的文件大小相符；截图的约 177 KB/s 是过程中的瞬时值，与全程平均值处于同一量级。两条数据库记录均已完成，`relayed=0`。耗时包含应答、开流、接收及最终校验，不能当成纯链路测速；但它足以确认用户实际等待确实很慢。

相同传输起始时刻的日志明确记录：

```text
23:12:55.838  不是局域网直连，隔空传送不走快速通道 local=host remote=srflx
23:14:42.456  不是局域网直连，隔空传送不走快速通道 local=host remote=srflx
```

`srflx` 是经 NAT 映射发现的公网地址，**不是中转服务器地址**；TURN 对应 `relay`。连接状态日志也显示这两次传送期间为 `direct`，并没有在传输期间切换到中转。

当前网络诊断另显示：Mac 有多个公网出口，对端不在局域网发现列表中。它确认了网络环境有多出口，不能据此单独认定选错出口或某个运营商限速。

## 2. 为什么直连不等于局域网快速通道

当前实际路径是：

```text
远端 Windows 文件
  → 文件帧 + zstd
  → 可靠、有序的 WebRTC DataChannel
  → SCTP / DTLS / ICE / UDP
  → 公网与两端 NAT
  → Mac 解压、写盘、SHA-256 校验
```

直连只说明文件数据不经 TURN 转发，公网路径仍受两边上/下行、跨运营商路由、UDP 丢包与时延影响。

2.5.1 的 TCP 提速专门针对满足条件的局域网路径。当前 `Peer.LANAddr()` 需要本端 candidate 为 host、对端为 host 或 prflx；本次远端为 srflx，因此拒绝开启快速通道。这是现有实现的预期选择，并非 2.5.2 的雷达改动改变了网络通道。

2.5.1 文档中的 144.3 MB/s 是 Mac → 本机 Linux 虚拟机的局域网 TCP 实测，不能套用到这条公网线路。

代码位置：

- `client-core/internal/transport/p2p/peer.go`：`LANAddr`、`OpenStream`。
- `client-core/cmd/pasteferryd/send_lan.go`：`lanHooks`。
- `client-core/internal/send/pipe.go`：`openPipe`、`openDataChannel`。

## 3. 代码检查发现什么

### 已确认

- 文件数据通道设置为可靠、有序；每条应用消息最多 60 KiB。
- Pion SCTP 当前默认初始 MTU 是 1191 B，较大的应用消息会被拆成多个网络分片。
- 发送缓冲高水位是 1 MiB，超过时每 2 ms 检查一次；这属于背压控制，并不是固定 177 KB/s 的速率限制。
- 收发帧流用 zstd，逐文件 SHA-256 校验；当前帧流顺序消费，前面缺失的数据会阻挡后续内容交付。
- 检查的 Send Files 与 P2P 数据通道代码中没有发现针对公网直连的 177/200/250 KB/s 固定限速。
- 这两次传送走直连，不能拿官方中转的速率政策直接解释它们。

### 需要测量后才能确认的嫌疑

| 嫌疑 | 为什么值得查 | 现阶段不能下的结论 |
| --- | --- | --- |
| 发送端实际可用上行或 UDP 流量整形 | 约 1.3 Mbit/s 的可用上行就足以产生观察到的结果 | 没有发送端测速，不能说它的宽带上行一定只有这个数 |
| UDP 丢包、RTT、抖动触发 SCTP 拥塞退让 | 可靠、有序、多分片传输对这些因素敏感 | 没有同期 RTT、丢包和重传计数，不能声称已经证明丢包 |
| 多出口中的路径质量 | 本机确实是多出口网络，选中的直连路径不一定最快 | 现有记录不足以判断选错了哪条线路 |
| 发送端磁盘/杀毒/CPU，接收端写盘 | 文件会读盘、压缩、校验、写盘 | 局域网先前测得快，不能排除本次远端机器的局部负载 |
| 应用背压与压缩缓冲在高时延下的行为 | 目前缺少各阶段等待时间，无法分清是在等网络还是等处理 | 不能凭 1 MiB 缓冲大小断定改大就有效 |

## 4. 后续修复前应补齐的测量

1. **同一时段、同一对端、双向对照**：用明确的测试文件测远端 → Mac 与 Mac → 远端，分开记录协商/开流时间与数据时间。当前没有为了排查而主动给公网对端投送文件。
2. **记录真实候选路径和运输层指标**：选中的 candidate 对类型、实际文件通道（TCP / DataChannel）、RTT、SCTP 拥塞窗口、重传与缓冲等待。日志中避免长期记录公网 IP 与真实文件名。
3. **同线路 TCP 与 UDP 对照**：两端可控时，测 TCP 吞吐、UDP 丢包/抖动，再与 DataChannel 比较。若 TCP 同样慢，优先查线路与发送端；若 TCP 快、DataChannel 慢，再聚焦 SCTP 与 UDP 路径。
4. **高时延/丢包的可控复现**：例如 RTT 20/80/150 ms，丢包 0/0.1/1%，比较消息分片、发送水位、SCTP 配置的影响，先拿到结果再改参数。
5. **界面区分「局域网 TCP 直连」与「公网 WebRTC 直连」**：让用户知道当前实际使用的通道，避免把「直连」理解成保证高速。这属于后续改进建议，本次未实现。

不建议直接取消可靠/有序传输、关闭校验，或把 TCP 无条件拨向公网映射端口。UDP 打洞成功并不意味着相同端口的 TCP 可达，任何新通道都要保持配对身份认证、加密与自动回退。
