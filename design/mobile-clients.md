# 隔空贴 Android / iOS 客户端方案

> 评审稿 · 2026-10-09 · 基于仓库提交 `59ba977`（客户端 1.3.1）
>
> 2026-10-27：Android 部分已按 2.6.3 的代码和新的调研重写，见 [phone-sync.md](phone-sync.md)（与手机网页传输合并在一起）；iOS 暂不做，新的调研结论见那份的 5.3 节，本文的 iOS 部分仍可参考。
>
> 本文是实施建议，不代表移动端已经实现。代码现状已核查；平台规则参考官方资料，实际构建、性能和真机兼容性需要通过第一阶段验证。

## 1. 结论与建议

**Android 和 iOS 都有可落地方案。建议做成“手机与电脑之间的内容传送与剪贴板收件箱”，复用 Flutter 界面和 Go 通信核心。**

手机端的主要入口是：系统分享、主动粘贴、文件选择；收到内容后，可以复制、保存或分享给其他 App。桌面端继续保留自动监听剪贴板的体验。

需要接受的产品边界：

- **Android：**Android 10 起，普通后台 App 无法任意读取其他 App 的剪贴板；前台服务和常驻通知也不会解除这个限制。可以做好主动发送、前台接收，以及受系统限制的后台传输。
- **iOS：**普通 App 不能长期在后台监听剪贴板或维持任意 P2P 连接。可以做好主动粘贴、分享导入、前台传输和收件箱。推送不能保证及时唤醒，更不能保证在后台自动复制。
- **如果必须实现“任何 App 复制后，手机锁屏也能立即与电脑双向自动同步”，不建议按普通 Android / iOS App 立项。**这不是更换 Flutter 或 Go 就能解决的问题。

推荐分两期：

| 阶段 | 用户能得到什么 | 投入与取舍 |
|---|---|---|
| 一期：在线互传 | 手机与 Mac / Windows 互传文字、图片、文件；接收后点一下复制；断开后保留发送任务，重新在线时重试 | 推荐先做；沿用信令 + TURN，不增加云端内容存储；传输时需要双方同时在线 |
| 二期：离线投递 | 接收方离线也能暂存投递，稍后打开 App 下载；可选推送提醒 | 增加端到端加密的临时存储、投递服务、配额、删除与推送维护成本 |

**优先顺序：共用核心验证 → Android 可用版 → iOS 可用版 → 再决定是否投入离线投递。**第一阶段就验证 iOS 构建和分享扩展，避免到最后才发现技术路线不通。

## 2. 用户实际怎么用

### 2.1 手机发送到电脑

**Android：**

1. 在浏览器、相册、聊天软件或文件管理器中，选择内容并点击“分享 → 隔空贴”。
2. 隔空贴打开接收分享的页面，选择目标设备，预览后发送。
3. 电脑收到后按现有设置写入剪贴板或复制记录，随后可直接粘贴。
4. 电脑离线时显示“等待设备上线”；用户重新打开手机 App 且电脑在线后重试，不把排队显示成发送成功。

已经复制的文字，也可以打开隔空贴，点击“粘贴并发送”。不自动读取每次进入 App 时的剪贴板。

**iOS：**

- 最可靠的主流程：打开隔空贴 → 使用系统粘贴控件或选择照片 / 文件 → 选择电脑 → 发送。
- 一期系统分享入口：分享扩展把内容保存为发送草稿，提示“已保存到隔空贴，请打开 App 发送”；用户随后手动打开主 App 完成传输。
- “在分享面板里直接发完”作为后续优化，必须先验证扩展的内存、运行时间、网络握手与宿主退出行为。**不承诺分享扩展能自动拉起主 App，也不把仅保存草稿标为已发送。**

后一条意味着 iOS 一期比 Android 多一步，需要在内测时确认用户能否接受。

### 2.2 电脑发送到手机

1. 在电脑复制文字、图片或文件。
2. 手机打开隔空贴，建立连接并接收当前内容或仍可补发的记录。
3. 文字点击“复制”，图片点击“复制 / 保存 / 分享”，文件点击“保存到文件 / 分享”。
4. 手机切回微信、邮件等目标 App 粘贴；图片能否直接粘贴取决于目标 App 支持的格式。

默认只进入手机收件箱，不自动覆盖手机已有剪贴板。后台收到提示也不等于内容已下载，更不等于已写入剪贴板。

一期要求内容来源设备在线、记录未过期且源文件仍可读取。电脑已经关机时，手机不能从只有信令和 TURN 的服务器取回内容。

### 2.3 内容范围

| 内容 | 一期交付 | 边界 |
|---|---|---|
| 文字、链接 | 双向发送、预览、复制 | 默认显式操作后发送 |
| 富文本 | 接收后优先展示 / 复制纯文本 | 保留协议兼容；跨 App 样式一致性不作为一期承诺 |
| 图片 | 原文件分享；剪贴板位图按现有 PNG 语义处理 | HEIC 等原图作为文件传送，预览另生成缩略图；大图避免整张解码占内存 |
| 单个 / 多个文件 | 导入、传输、保存、系统分享 | 使用 App 沙盒暂存与系统文件选择器，不依赖桌面绝对路径 |
| 文件夹 | 电脑发来的目录可作为一组文件接收；移动端对外导出 ZIP | 一期不做手机端任意目录监听；手机发送文件夹需先打包，ZIP 是文件而非桌面剪贴板目录语义 |
| 历史记录 | 本机收件箱、来源设备、状态、过期和清理 | 不等同于全设备永久云历史 |

手机到手机也走相同协议，但一期验收优先覆盖 Android / iOS 分别与 Mac / Windows 互通，再覆盖 Android ↔ iOS。

## 3. 平台能力与限制

| 能力 | Android | iOS |
|---|---|---|
| 后台监听其他 App 的复制 | 普通 App 不可依赖；Android 10+ 限制，默认输入法等特定例外不作为本产品前提 | 无通用、长期后台监听方案 |
| 用户主动粘贴 | App 有焦点时读取；用户明确点击触发 | 使用 `UIPasteControl` 等系统粘贴交互；程序化读取可能弹出许可提示 |
| 系统分享导入 | `ACTION_SEND` / `ACTION_SEND_MULTIPLE` | Share Extension + App Group |
| App 前台实时接收 | 可做 | 可做 |
| 退后台继续传输 | 对符合条件的用户发起传输，可申请合适的前台服务；受类型、启动、时限与厂商策略约束 | 允许有限的收尾时间；到期保存任务并停止，不能把它当常驻网络进程 |
| App 被杀后自动恢复 | 系统调度不确定；强行停止后不能承诺恢复 | 不能承诺自动恢复任意 P2P 会话；重新打开后恢复待办 |
| 离线提醒 | 后续可接推送；中国大陆还需考虑厂商渠道 | 后续可接 APNs；静默推送可能延迟、限流或不送达 |
| 手机收到后自动写剪贴板 | 一期不用此体验，默认点击复制 | 一期不用此体验，默认点击复制 |

具体实施原则：

- Android 前台服务只服务于用户正在执行的合法传输场景，不把“常驻服务”当读取剪贴板的权限。面向 Android 15+ 的 `dataSync` 服务受后台累计时限约束：官方规则为 24 小时内总计 6 小时，用户把 App 带回前台会重置计时；不能设计成全天候保活，上线前按实际 target SDK 复核新规则。
- iOS 的 `BGTaskScheduler`、静默推送和较新系统上的后台任务 API，都不应被解释为任意后台常驻权限。新版用户发起的持续任务能力可以专项验证，但不作为最低版本或实时接收承诺的基础。
- iOS 后台 `URLSession` 适用于系统支持的 HTTP(S) 上传下载，不能直接托管现有 Go WebRTC DataChannel；二期若需要系统接管传输，必须增加相应的 HTTPS 密文传输路径。
- 不采用 root、ADB 授权、辅助功能抓取、伪装音频 / VoIP / VPN 保活等作为正式产品依赖。输入法可作为独立产品方向另评估，不纳入本期。

建议最低系统：**Android 10（API 29）、iOS 16**。这是产品建议，不是已经验证的工具链兼容结论；第一阶段核查 Flutter、Go、NDK、Xcode 与依赖支持情况。发布时的 target SDK 和商店要求另按当时规则确定。

## 4. 现有项目能复用多少

当前仓库只有 macOS / Windows 平台工程，不能直接执行一次 Flutter 移动端打包就交付。

| 当前代码 | 可复用部分 | 必要改造 |
|---|---|---|
| `ui/lib/pages/`、`app_state.dart` | 配对、历史、设置的数据模型和部分组件、多语言 | 手机导航和触控布局；状态层解除对 `DaemonConnection` 的直接依赖 |
| `ui/lib/daemon_client.dart`、`background_service.dart`、`platform.dart` | 桌面适配继续保留 | 现有实现依赖 `daemon.json`、本机 gRPC、进程启动、桌面目录；移动端改为应用内调用和系统 API |
| `client-core/internal/transport/` | WebSocket 信令、Pion WebRTC、签名连接、直连 / TURN | 前后台停止与恢复、网络切换、耗电策略、IPv6 / NAT64 真机验证 |
| `client-core/internal/sync/` | 内容记录、打包分流、传输进度、接收流程 | 输入目前通过 `clipboard.Watcher` 读取；增加主动提交内容、指定接收设备、接收策略与可取消生命周期 |
| `client-core/internal/clipboard/` | 内容模型和桌面实现 | 增加移动端宿主接口；macOS 的 `darwin` / Cocoa 构建约束需排除 iOS，不能把 iOS 当 Mac 编译 |
| `store/`、`cache/`、`pack/` | 存储、缓存、流式打包与安全解包逻辑 | 验证 `modernc.org/sqlite` 的移动目标支持；沙盒路径由宿主注入；增加磁盘限额与持久化投递任务 |
| `identity/` | Ed25519 身份、设备 ID、指纹配对 | 当前非 Windows 私钥按文件权限保护；移动端改为系统安全存储适配 |
| `proto/` | 现有配对、信令、内容消息、文件传输格式 | 增加能力协商、投递回执和接收策略；兼容旧版本 |
| `server/` | 一期信令、配对、TURN 服务主体 | 配置 WSS；当前 TURN 为 UDP，要评估受限网络的中转补充；二期才增加内容暂存与推送 |

**预期通信与内容处理逻辑复用较多，生命周期、系统分享、文件权限和移动界面需要新增。**在跨编译和真机 PoC 完成前，不给出“复用率 80%”一类未经测量的承诺。

## 5. 推荐技术架构

```text
Flutter：收件箱 / 发送 / 设备 / 设置
                  │
           CoreClient 抽象接口
                  │
      MethodChannel / EventChannel
                  │
     Kotlin / Swift 移动端宿主
       ├── 剪贴板、分享、文件选择、权限、安全存储
       ├── 前后台生命周期与网络变化
       └── gomobile 绑定的 Go Core
             ├── 配对 / 签名 / 同步引擎
             ├── 记录 / 缓存 / 持久化发送任务
             └── WSS 信令 + WebRTC（直连 / TURN）
                           │
                 Mac / Windows / 其他手机

iOS Share Extension → App Group 中的导入草稿
                            ↓ 主 App 下次启动时消费
                       Flutter 发送页面
```

### 5.1 桥接与核心拆分

首选 `gomobile bind`：Android 产出 AAR，iOS 产出 XCFramework，经 Kotlin / Swift 接给 Flutter。桌面仍使用现有 gRPC 适配器；移动端在应用进程内嵌入核心，不启动 `pasteferryd` 子进程。

建议新增 `client-core/mobile/` 门面与 `internal/runtime/`，从 `cmd/pasteferryd/main.go` 抽出可启停的组装逻辑。门面只暴露绑定支持的基本类型、字节数组、简单接口，不直接暴露 Go 泛型、channel、context 或复杂 Protobuf 类型。

建议接口语义（名称待实现时确定）：

- `Start(config, paths)` / `Suspend()` / `Resume()` / `Close()`：可重复调用，正确释放 socket、计时器和 goroutine。
- `SubmitContent(content, targetDeviceIDs)`：直接提交内容；新增按设备发送能力，不能沿用“广播所有配对设备”后却在 UI 上假装单选发送。
- `Fetch(clipID)` / `Cancel(taskID)` / `Retry(taskID)`：可取消和重试；一期断线后重新传整个文件，不承诺按字节断点续传。
- 查询历史、管理配对、订阅状态与进度：复用现有语义，事件经平台桥返回 UI。
- 系统剪贴板操作由 Kotlin / Swift 在平台要求的线程执行；Go 核心不占用 Flutter 主线程运行桌面 `MainLoop`。

跨桥仅传递描述信息、受控文件路径和小消息。文件采用流式处理，不把几十 MB 内容作为 Dart ↔ Java / Swift ↔ Go 的多份字节数组传递。

第一阶段必须验证 Go 1.26.3、Pion、SQLite、压缩库在 Android arm64、iOS 真机 arm64 与模拟器目标上的构建和运行。`darwin` 标签、Cocoa 链接和图片转换分别审计，不能仅通过改一个文件名判定可用。

若绑定受阻：先定位是 SQLite、构建约束还是 Go 绑定边界，局部替换存储或采用 C ABI + Dart FFI；只有核心依赖确实无法支持移动目标时，才评估重写传输层。更换桥接方式本身不会解除 iOS 后台限制。

### 5.2 为什么不优先重写

| 路线 | 优点 | 主要代价 | 建议 |
|---|---|---|---|
| Flutter + 内嵌 Go + 少量原生宿主 | 复用现有配对、安全协议、打洞和传输经验 | 需要验证绑定、构建与生命周期 | 首选 |
| Flutter + Dart / 原生 WebRTC 重写核心 | Flutter 侧集成直观 | 重新实现签名协议、数据通道、压缩、重连和 NAT 优化；互通回归面大 | 作为核心移植失败后的备选 |
| Swift + Kotlin 两套完整客户端 | 最贴近平台 | 两套界面和业务逻辑，维护成本最高；仍然受后台限制 | 本期不选 |
| PWA / 网页 | 分发简单 | 剪贴板、分享入口、文件与后台能力难满足目标 | 只适合未来临时传文件入口 |

## 6. 一期必须解决的工程问题

### 6.1 持久化投递和明确状态

当前 `sync/backlog.go` 每个设备只在内存中保留最近 20 条、最长 24 小时的补发记录，进程重启就清空。手机经常被挂起或终止，不能把这个机制作为可靠投递。

新增本地 outbox，按“内容 ID + 目标设备 ID”保存：状态、重试次数、过期时间、源文件、错误原因。至少区分：草稿、等待上线、发送中、等待回执、已接收、失败、已过期。每个目标独立计数，避免一台成功就误报全部成功。

- 任务和内容落盘后，才显示“已加入发送队列”。系统分享的临时 URI / URL 在权限结束前复制到受控目录；空间不足时明确失败。
- 文本在接收方成功落库后回执；文件在落盘和完整性验证后回执。现有发送结束消息不能直接代替接收端确认。
- 回执丢失时允许重发，以来源设备和内容 ID 去重，避免多条历史和重复覆盖剪贴板；仅接受已配对设备的有效回执。
- 进程重启后把未完成任务恢复为可重试；重连补发默认只进历史，不覆盖当前剪贴板。
- 历史和文件缓存的清理必须考虑未完成任务；任务到期后释放引用，不能无限期占用空间。
- 桌面源文件若只引用原路径，仍可能被移动或删除。只有做了受配额约束的快照，才能承诺其内容在等待期间保持不变；源文件消失时显示“源文件不可用”。

移动端和桌面端需要一起增加持久化投递能力，才能可靠覆盖“电脑复制后重启，稍后手机再打开”的场景。

### 6.2 旧版本互通与手机流量

新增能力握手，例如协议版本、可接收类型、自动接收上限、回执支持。保留已有 Protobuf 字段编号，只加新字段 / 消息；通过明确协商决定是否启用新行为，不能只凭“未知字段会忽略”认定协议升级安全。

建议一期配套发布桌面升级版，按接收设备的策略发送：手机在蜂窝网络下默认只接收元数据和小文本，附件手动拉取；Wi-Fi 下可自动收取小附件。

旧桌面端可能无视手机策略，按自身 50 MiB 阈值推送。对这类设备显示兼容模式：不承诺蜂窝流量控制和可靠回执，必要时禁止在蜂窝网络连接该设备并提示升级。旧端没有回执时显示“已发出，未确认”，不能显示“已接收”。

建议的初始配置值，均待压测后调整：

- Wi-Fi 自动接收附件上限 10 MiB，蜂窝网络默认手动；大附件只先显示记录。
- 本地记录默认保留 3 天，缓存预算 500 MiB，单任务暂定上限 100 MiB；超限可提示使用电脑或另行确认。
- 缓存超额、磁盘不足、压缩包解压体积或条目超限时停止接收并提供原因，不因“压缩包很小”跳过限制。

### 6.3 Android 宿主

- 处理单项和多项系统分享，通过 `ContentResolver` 读取 `content://`，不把 URI 当文件系统路径。
- 使用 Storage Access Framework 导入 / 导出，向其他 App 分享时提供有期限的 URI 读取权限；不申请无必要的“所有文件访问”权限。
- Kotlin 宿主持有单一 Go Core 实例，Activity 重建时不重复启动；前台服务也不另起第二个核心。
- 用户发起的传输确需在后台继续时，再使用符合用途的前台服务，提供进度、取消和超时处理；不把 WorkManager 用作常驻实时 socket。
- 按需申请通知权限。检测省电 / 厂商后台限制，用可理解的状态说明，不承诺提示用户关掉省电后就永不掉线。

### 6.4 iOS 宿主与分享扩展

- Swift Share Extension 一期只负责 `NSItemProvider` 读取、类型检查、限额、复制文件和写入草稿清单，不在扩展中加载 Flutter 和整套 P2P 核心。
- 通过 App Group 交换文件；草稿采用临时文件 + 原子提交，主 App 幂等消费，处理扩展中途退出。主 App 独占业务数据库写入，避免两个进程并发运行 Go 核心。
- 从文件选择器获得的 security-scoped URL，按规则访问并及时导入本机目录，不把短期权限当长期路径。
- 前台活动时连接；离开前台后在系统允许的收尾时间内完成或中止，保存任务，关闭无需保留的连接；回到前台后重新探测网络并重连。
- 局域网访问、照片保存、通知等权限只在相关功能需要时申请。权限被拒绝时给出明确反馈和仍可用的操作。
- 一期不做 File Provider、键盘扩展；Shortcuts / App Intents 在主流程稳定后可增加“发送传入内容”等快捷动作，仍由系统限制实际执行时间。

### 6.5 网络与本地数据

沿用已配对身份校验和 WebRTC DTLS 加密。信令部署改用有效证书的 `wss://`；不通过全局关闭 ATS 或全局放开 Android 明文网络来解决部署问题。

当前 `server/relay/turn.go` 只配置 IPv4 UDP TURN。**WSS 只能保障信令可达，不能让完全禁 UDP 的网络自动完成文件传输。**第一阶段必须验证蜂窝、IPv6 / NAT64 和企业网络。若受限网络是首发目标，应单独加入 TURN/TCP / TLS 的服务与客户端互通验证；“监听 443”本身不代表一定能穿过代理。

移动端在前台或显式传输时才进行积极探测；后台停止高频 STUN 和中转升级重试。Wi-Fi ↔ 蜂窝切换时更新网络代次，终止旧连接上的任务，重连后重试，避免继续向失效数据通道写入。

安全存储建议：iOS 用 Keychain 保存身份密钥材料；Android 用 Keystore 中的密钥加密封装现有 Ed25519 私钥。不假设所有 Android 设备都支持硬件 Ed25519，也不把现有 Ed25519 直接改成其他算法破坏配对协议。密钥访问、App 卸载重装、备份恢复都需定义行为并验证。

历史和缓存默认放应用私有目录，排除不必要的系统云备份；iOS 使用合适的数据保护等级。日志不记录复制正文、密钥或文件内容；通知默认只显示来源和类型。Android 的敏感剪贴板标记如可读到应予尊重，但不能承诺识别所有密码或敏感内容。

## 7. 二期：对方离线也能投递

只有一期验证了使用频率和需求后，再增加密文临时投递服务。

```text
发送端：生成内容密钥 → 加密内容与敏感元数据 → HTTPS 上传密文
              │
     投递服务保存收件人信封、密文对象和有效期
              │ 可选 APNs / Android 推送：仅“有新内容”
              ▼
接收端打开 App：认证 → 下载密文 → 解密 → 校验 → 回执 → 按策略删除
```

必须明确的新增成本与设计：

- 现有 DTLS 只保护在线传输，不会自动保护对象存储。离线内容需要独立、经审查的端到端加密信封方案。
- 现有 Ed25519 用于签名，不能直接当内容加密算法。可评估独立 X25519 密钥协商 / HPKE 等成熟方案，由原有配对身份签名绑定新的加密公钥，明确密钥轮换、撤销和兼容规则。
- 文件名、文本预览和内容正文一并加密；服务端仍会看到路由设备、访问时间、密文体积等必要元数据，应在说明中如实披露。
- 为每个接收设备封装密钥；设置容量、保留期、上传下载授权、速率限制和回执后的清理策略。撤销设备只能阻止后续访问，不能收回它已下载解密的内容。
- HTTPS 密文文件可以交给 iOS 后台 `URLSession` 等系统机制；调度仍由系统决定，不能承诺实时完成。
- 推送只提示有待取内容，不放正文。APNs / FCM 及厂商推送均为可选依赖，关闭通知仍可在打开 App 时获取内容。
- 自建用户可以只启用在线模式；若要推送，需要解释推送网关或相应凭据的部署方式，不能宣称现有单二进制服务无需配置就有推送。

成本按密文存储量、保留时长、下载流量和请求量计算；一期则主要是现有 TURN 中转带宽。暂不在没有设备量、文件规模和供应商报价的情况下给出月费数字。

## 8. 实施计划与投入

假设两名熟悉 Flutter / Go / 原生桥接的工程师，测试与发布协作约 0.5 人；以下为工程估算，不是交付承诺，不含商店外部审核等待。

| 阶段 | 日历时间估算 | 可评审产物与进入下一阶段条件 |
|---|---|---|
| P0：关键验证 | 第 1–2 周 | Android / iOS 真机运行内嵌 Go；与现有电脑完成配对、文本和 10 MiB 文件互传；SQLite 重启恢复；iOS 扩展草稿导入；形成继续 / 调整路线的结论 |
| P1：共用核心与桌面适配 | 第 3–5 周 | 核心生命周期接口、移动桥接、持久化任务、回执 / 能力协商、按目标设备发送；桌面回归通过 |
| P2：Android 内测 | 第 6–8 周 | 分享入口、发送 / 收件箱、文件权限、有限后台传输、网络切换；签名 APK 内测 |
| P3：iOS 内测 | 第 9–11 周 | 系统粘贴控件、分享扩展、App Group、前后台恢复、导出 / 分享；TestFlight 内测 |
| P4：稳定与发布准备 | 第 12–14 周 | 手机 × 桌面互通矩阵、耗电 / 存储检查、升级迁移、权限说明、隐私说明与发布材料 |

Android 首个可用内测目标约 **6–8 周**，两端达到可发布质量约 **12–14 周**。单人承担全部工作初步按 **20–28 周**规划；P0 结束后依据实测重新估算。

二期离线投递另估 **6–10 周 / 两名工程师**，含服务端、加密信封、推送和删除验证。若一期要求完整云离线体验、系统分享面板内直接发送、按块断点续传或广泛厂商推送覆盖，需要重排计划。

必要资源：Mac + Xcode、Android SDK / NDK、Apple 开发者账号、签名与 CI 密钥管理、iPhone 真机、至少 Pixel / 三星 / 一种国内 Android 系统真机，以及可观测的 WSS / TURN 测试环境。Android 分发优先签名 APK 内测；商店上架要求按分发地区另核对。

## 9. 验收标准

下列数值是建议验收目标，尚未测量；P0 固定网络、设备和构建条件后修订。

| 项目 | 验收条件 |
|---|---|
| 核心互通 | Android / iOS 各自与 Mac / Windows 双向配对、文字、图片、多文件互传；Android ↔ iOS 做基本互通验证 |
| 传输正确性 | 固定 1 MiB、10 MiB、100 MiB 样本，接收端与源文件 SHA-256 一致；取消 / 重试后没有可被误打开的残缺文件 |
| 交互时延 | 双端前台、连接已建立、稳定局域网下，小文本到收件箱 P95 ≤ 1 秒；冷启动建连与公网中转另行记录，不混用指标 |
| 生命周期 | 发送中退后台、锁屏、进程终止、重新打开；任务恢复或明确失败，不虚报已送达；回执丢失重试不产生重复记录 |
| 网络 | 同网 Wi-Fi、跨网、蜂窝、Wi-Fi 切换、TURN 强制中转、IPv6 / NAT64；纯 UDP 被阻断时，要么经验证的备用传输成功，要么明确提示不可达 |
| 权限与存储 | 拒绝剪贴板 / 文件 / 通知相关权限、临时 URI 失效、磁盘不足、大图、解压超限均可恢复；不会反复弹权限提示 |
| 协议兼容 | 新手机 ↔ 新桌面完整能力；新手机 ↔ 旧桌面准确显示降级；不改变既有 Mac ↔ Windows 的自动同步行为 |
| 隐私与资源 | 正文不进入日志 / 通知；默认不后台轮询剪贴板；暂停后释放网络任务；真机观察温升、内存与耗电，相对无 App 基线记录结果 |

测试重点放在接口拆分、投递状态、权限、真机生命周期和互通行为，不用“模拟器能启动”代替移动端可用性证明。

## 10. 建议本次确认的产品范围

推荐以以下范围进入 P0，无需先决定云存储供应商：

1. 两端一期都接受“主动发送 + 前台接收 + 点击复制”；不宣传全天候自动剪贴板同步。
2. Android 先内测；iOS 一期分享扩展接受“保存草稿，打开主 App 发送”的多一步流程。
3. 一期保持服务器不存用户内容；接收方离线时由发送设备本地保留任务，之后双方同时在线再送达。
4. 配套升级桌面端，补齐持久化任务、回执和手机接收策略；旧版保留有限兼容。
5. 离线投递、推送、分享扩展直接发送、断点续传和键盘扩展均另行排期。
