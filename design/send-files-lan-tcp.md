# 隔空传送：局域网快速通道（2.5.1）

状态：方案，待审核。主方案见 [send-files.md](send-files.md)，测速依据见其中第 12.1 节。

## 1. 目标

两台电脑在同一局域网（或同在 Tailscale 里）时，隔空传送的文件数据改走一条 TCP 连接，千兆有线网从现在的约 19 MB/s 提到接近跑满（约 100 MB/s）。

不变的东西：

- 外网直连和中转照旧走现在的 WebRTC 数据通道。
- 发送请求、应答、取消、结果这些控制消息照旧走现在的控制通道，只有文件数据换管道。
- 帧格式、断点续传、逐文件 SHA-256、进度、通知、界面都不改。
- 现有数据通道的代码一行逻辑都不改，只把它包成「管道」的一种实现。
- 任何一步失败都退回数据通道，用户感觉不到差别，只是慢一些。

这是性能改进，版本号 2.5.1。

## 2. 什么时候走 TCP

三个条件同时满足才试 TCP，缺一个就直接用数据通道：

1. 对方声明支持：能力列表里有 `send_files_tcp_v1`（2.5.1 起）。
2. 当前的 WebRTC 连接是局域网直连：选中的 candidate 对里，本端是 host（本机网卡上的真实地址），对端是 host 或 prflx。经 TURN 中转（relay）、经 NAT 映射（srflx）的连接都不算。Tailscale 的 100.x 地址也是 host，会走 TCP。
3. 接收方能在这个地址上监听 TCP 端口。

第 2 条直接复用 ICE 已经打通的那条路，地址是现成的，不用猜，也不会去碰外网地址。

## 3. 流程

```
发送方                                    接收方
  │ SendOffer（不变）                       │
  │ ──────────────────────────────────────▶ │ 接受；满足第 2 节的条件时，
  │                                        │ 在本端 host 地址上开一个临时 TCP 端口
  │ SendAnswer（多一个 lan_addr）            │
  │ ◀────────────────────────────────────── │
  │ 有 lan_addr：拨号 + TLS 握手（2 秒超时）  │
  │ ══════════════ TCP ═══════════════════▶ │ 核对对方身份，读到数据流标签
  │ 帧流（不变）                             │ 交给原来的接收流程
  │ ══════════════════════════════════════▶ │
  │ SendResult（不变）                      │
  │ ◀────────────────────────────────────── │
```

- 接收方的临时端口只接一次连接，连上或这次尝试结束（超时、取消、完成）就关掉。不常驻监听，不新增固定端口。
- 发送方连不上、握手失败或超时，就照原来的方式开数据通道，接收方两条路都在等，先到哪条用哪条。
- 续传时（新的一次尝试）重新走一遍判断，可能这次走 TCP、下次走数据通道，帧流从断点接着发，与管道无关。

## 4. 认证与加密

- TLS 1.3，两端都出示证书，证书的公钥就是设备身份的 Ed25519 密钥（配对时已核对过指纹的那把）。证书在后台服务启动时从身份密钥现生成，只在内存里。
- 接收方核对：连过来的证书公钥算出的设备 ID，必须等于这次传输的发送方。发送方同样核对接收方。对不上立即断开。不需要另发口令。
- 握手后发送方先写一行数据流标签（`send:<传输 ID>:<第几次尝试>`，与数据通道的标签相同），接收方用原来的规则核对，对不上就丢弃。
- 安全性与现在的数据通道相同：端到端加密，第三方看不到内容，也冒充不了设备。

## 5. 卡住与断线

- TCP 打开 keepalive（15 秒）。
- 发送方每次写入设 30 秒超时，对方睡眠或拔网线时写入会报错，按现在的方式标为中断、等重连后续传。
- 接收方原有的看门狗（一段时间收不到数据就中断）照样生效。
- 取消：原来取消时关数据通道，现在关当前这条管道，两种管道都一样。

## 8. 防火墙

- **Windows**：第一次运行时系统弹窗点了允许，会同时放行 TCP 和 UDP，不用做什么。之前用设置里的「放行」按钮加的规则只有 UDP，TCP 入站会被挡，这时自动退回数据通道；2.5.1 的「放行」按钮会把 TCP 也加上。要实测：接收方第一次开 TCP 端口时会不会再弹一次防火墙询问。
- **macOS**：后台服务已有「本地网络」权限。系统防火墙默认关闭；用户打开了的话要实测会不会询问。
- **Linux**：Ubuntu 默认不启用 ufw。启用了的话 TCP 被挡，退回数据通道。

## 9. 测试

**自动测试**

- `lantcp`：见第 6 节。
- `send`：在现有两个后台服务互发的测试里，加上 `ListenLAN`、`DialLAN`：
  - 走 TCP 发文件和文件夹，内容一致
  - TCP 上中断后续传
  - TCP 上取消
  - 拨号失败时退回数据通道
  - 对方不支持时不开端口
- 原有的 `send` 测试不带这两个函数，照样全部通过，证明不设置时行为不变。

**实机测试**

| 线路 | 看什么 |
| --- | --- |
| Mac ↔ 局域网里的 Windows 台式机 | 速度（目标约 100 MB/s）、防火墙会不会弹窗 |
| Mac ↔ Linux 虚拟机、Mac ↔ Windows 虚拟机 | 两个方向、杀进程续传、取消 |
| 一端 2.5.0、一端 2.5.1 | 退回数据通道，照常传完 |
| Windows 上用防火墙挡住 TCP | 退回数据通道，照常传完 |
| 官方服务中转（外网） | 不走 TCP，行为与 2.5.0 相同 |
