# 多出口网络的 NAT 打洞

> 状态：已实现。多出口探测随 1.1.0 发布（2026-10-08）；中转后换直连、连接失效检测与补发随 1.1.1 发布（2026-10-09）；谁先发包随 1.1.2 发布（2026-10-09）
> 代码：`client-core/internal/transport/p2p/egress*.go`、`manager.go`、`peer.go`；补发在 `client-core/internal/sync/backlog.go`
> 验证：`tools/natlab/`（NAT 打洞实验室，CI 中运行）

## 一、问题

两台 Mac 配对成功，同步也正常，但设备列表里一直显示「中转」：数据全部经服务器转发，速度被服务器带宽卡在约 0.6 MB/s。

两台设备分别在公司和家里。逐一排查后确认，打不通的根源是公司网络有多个出口。

## 二、测量

### 公司这台

从同一个本地 UDP 端口，向分布在不同网络的多台 STUN 服务器发 Binding 请求，记录每台服务器看到的本机公网地址。实测有 4 个不同的出口 IP，下文以出口 A–D 代称（公网地址不公开）：

| 出口 | 落在这个出口上的服务器 | 公网端口 |
|---|---|---|
| 出口 A | 自己的服务器（百度云北京）、Twilio | 与本地端口相同 |
| 出口 B | B 站、Google、Nextcloud | 与本地端口相同 |
| 出口 C | Cloudflare、FreeSWITCH | 改写，但对不同目标相同 |
| 出口 D | 阿里云上的服务、有时是 Google（经 Wi-Fi 时） | 改写 |

另外两组对照实验：

- **出口只按目标 IP 选择**。向同一台服务器的 8 个不同端口探测，全部从同一个出口出去、得到同一个公网端口。
- **同一线路上映射固定**。同一本地端口发往 Cloudflare 与 Twilio，看到的都是出口 C 上的同一个端口。

结论：公司网络等于 4 个并列的、各自「端点无关映射」的 NAT，按目标 IP 选择走哪一个。单看每一条都很好打洞，难点只在于「发往对端的包走哪一条」事先不知道。

公司路由器不支持 UPnP 与 NAT-PMP，也没有 IPv6。

### 家里这台

| 项目 | 结果 |
|---|---|
| 国内目标 | 同一本地端口发往不同服务器，公网地址与端口都相同：端点无关映射，好打洞 |
| 国外目标 | 经本机的代理出去，与隔空贴无关 |
| 路由器 | 支持 UPnP，但它自己的外网地址与服务器看到的地址不同：运营商还有一层 NAT，在路由器上映射端口没用 |
| IPv6 | 只有内网地址 |

### 旧版本为什么打不通

1. **只问了一台服务器**。客户端只从自己的服务器得知本机公网地址，即出口 A，也只把它告诉对端。发往对端的包按目标 IP 很可能从另外三个出口之一出去，对端收到的源地址与告诉它的不一致，被它的路由器当作陌生来源丢弃。
2. **多配几台 STUN 也没用**。pion 每问一台 STUN 服务器都单独开一个本地端口，问到的地址只对那个端口成立，互相用不上。

## 三、方案

### 1. 所有连接共用一个本地端口

`p2p.Manager` 启动时打开一个 UDP 端口，用 pion 的 `UniversalUDPMux` 包装，交给所有 `PeerConnection`（`SettingEngine.SetICEUDPMux`）。之后本机的所有连通性检查都从这个端口收发，于是「这个端口在每条线路上的公网地址」是一组固定、可知的值。

信令服务器下发的 STUN 地址不再交给 pion，改由本端在共享端口上探测；TURN 照常交给 pion 用于中转。打不开端口时退回 pion 的默认做法。

### 2. 探测每个出口

在共享端口上并发探测一组 IP 分散的服务器：信令服务器下发的 STUN，加上内置的公共服务器（B 站、Cloudflare、Twilio、Nextcloud、Google、FreeSWITCH）。实测 7 台服务器覆盖了公司全部出口。

- **按 IP 去重**：出口只按目标 IP 选择，同一 IP 的多个域名或端口探多少次都落在同一个出口。
- **过滤不可能是公网 STUN 的地址**：实测有域名被 DNS 污染到 `192.0.2.42`；代理软件的 fake-ip 常用 `198.18.0.0/15`。这些地址直接丢弃，不当成出口。
- **域名并发解析，每台 1.5 秒超时**。1.1.0 逐个解析域名，一台 DNS 慢就拖住整轮，实测整轮约 1.6 秒；1.1.1 改为并发后在 0.2 秒以内。启动时、服务器配置变化时、每 5 分钟、本机网络变化时、尝试换直连之前各探测一轮；探测进行中又被触发，结束后补一轮，不并发。

### 3. 把所有出口地址告诉对端

每个出口的公网地址作为一条 srflx candidate，在 offer 或 answer 之后经信令发给对端，最多 8 条。对端为每条建立 candidate pair 做连通性检查，与实际出口吻合的那一条能打通。

- 优先级按 RFC 8445 计算，实测地址排在推算地址之前。
- 会改写端口的线路，探测拿到的就是这个端口在该线路上的真实映射，不需要猜。
- 首轮探测还没结束时最多等 4 秒，免得刚上线就发一份空结果。这是在发出 offer/answer 之后的后台里等，不耽误握手，但要短于中转的等待时限。

### 4. 记住见过的出口

某一轮的探测服务器可能恰好都没落到某条线路上（实测出口 D 就时有时无）。本端按「本机各网卡的 IPv4 地址」区分网络，记下每个网络见过的出口 IP 及其是否改写端口，保存 7 天（`~/Library/Application Support/PasteFerry/egress.json`）。

不改写端口的线路，地址就是「出口 IP + 本地端口」，这一轮没探测到也可以推算出来补发给对端；会改写端口的线路无法推算，不补。

### 5. 优先直连

中转路径经服务器，握手往往比直连快。若不加约束，常常在直连打通之前就选中了中转，之后不再更换。中转路径要等一段时间才允许被选中（`SetRelayAcceptanceMinWait`）：1.1.0 是 3 秒，1.1.1 放宽到 5 秒，见第 8 节。

### 6. 两端显示一致

只有发送方能确定自己的数据是否走 TURN：对端经中转发来的包，在本端看来可能只是一个普通的 peer-reflexive 地址。连接就绪后两端经控制通道交换 `LinkInfo{relayed}`，任一端经中转，两端都显示「中转」（1.0.2 引入）。

### 7. 隐私开关与诊断

- 设置「用公共服务器探测网络出口」，默认开启。公共 STUN 服务器能看到本机公网 IP，与任何 WebRTC 应用相同，看不到内容。关闭后只用自己的服务器探测。配置字段 `only_own_stun` 刻意设计为「关闭」语义：旧版界面不发这个字段时，默认值 false 不会把功能误关。
- `pasteferry-cli nat`（后台接口 `GetNetwork`）显示打洞端口、每个出口的地址与来源，以及各设备当前走直连还是中转。

### 8. 落到中转后，再试直连（1.1.1）

**问题。**1.1.0 实机验收直连之后约 10 分钟，家里那台重启了后台服务，重连后变成了中转，之后一直是中转：

```
23:19:42  P2P 连接状态  direct
23:29:01  P2P 连接状态  offline      家里那台断开
23:29:06  P2P 连接状态  connecting   它重新上线，本端发起握手
23:29:10  P2P 连接状态  relay
```

这是一场赛跑。家里那台刚启动，要先探测完出口才能把出口地址发过来，而它访问部分公共 STUN 要经过代理，探测慢。出口地址到达之前，3 秒的中转等待时限已到，中转被选中。pion 选定 candidate 对之后不会再换，于是整个连接期间都走中转，哪怕直连其实打得通。

**做法。**

1. **缩短探测、放宽等待**：域名并发解析，整轮探测从约 1.6 秒降到 0.2 秒以内；中转等待从 3 秒放宽到 5 秒，比等待出口地址的上限（4 秒）长。
2. **中转时用 ICE 重启再打一次洞**：连接以中转就绪后，由发起连接的一方（不礼让方，两端规则一致，不会同时发起）安排一次尝试：先重新探测出口，再发一个 `ICERestart` 的 offer。两端重新收集地址、同时再打一次洞。打通就换成直连；仍打不通，还是落回中转，下次隔得更久再试：10 秒、30 秒、2 分钟、5 分钟、15 分钟，之后每 15 分钟一次。
3. **只在空闲时重启**：有数据流未关闭，或 10 秒内有过消息往来，就推迟。重启期间 pion 会清掉选中的 candidate 对，发出的数据暂时丢弃，由 SCTP 重传补上：连接不断、DTLS 与数据通道不变，只停顿几秒，但仍不该在传文件时做。
4. **用户手动「重新连接」（2.4.2）**：设备菜单里的「重新连接」不等上面的间隔，马上做一次 ICE 重启，有数据在传也照做；谁先发包接着自动重试轮流换，每次点都换一种顺序。已是直连时什么也不做；离线时马上在局域网里打招呼、信令断着的马上重连，找到就发起连接。只有发起方能重启：在应答方点的，经信令发一个签名的 `RetryDirect` 请发起方来做（旧版本不认识，照旧按自己的间隔重试）。官方服务的中转是另一条连接，中转照常用着，直连那条带上新的出口地址从头再打一次洞。界面最多等 15 秒，报告结果：已直连、仍经中转或对方不在线。

**ICE 重启要处理的细节：**

- **对端不能把它当成新握手**。应答方收到 offer 时，若连接已就绪且 DTLS 证书指纹没变，就是对端在重启 ICE：状态保持直连/中转，不打回「连接中」，也不启动 30 秒的握手超时，改由一个「重启 30 秒内没恢复就重置连接」的计时兜底（重启用的 offer 或 answer 若在信令里丢了，ICE 会一直停在检查中，自己不会失败）。
- **新一代 candidate 不能早于描述发出**。生成 offer/answer 时 pion 就开始收集地址，candidate 可能抢在描述之前发出；初次握手时对端会先缓存，重启时对端手里还是旧的远端描述，新 candidate 的 ufrag 对不上，pion 会直接丢弃。现在生成描述期间收集到的 candidate 先攒着，描述发出后再发。
- **信令不保序，接收端也要兜底**。candidate 的 ufrag 与当前远端描述对不上时，先缓存起来，设好新的远端描述后再加；缓存里混进的旧一代 candidate，补加时由 pion 按 ufrag 丢弃。
- **显示要能从「中转」改回「直连」**。1.0.2 的 `LinkInfo` 只会把状态改成中转。现在两端的视角合起来决定显示：重启后两端各自重新判断，再互发一次 `LinkInfo`，都不经中转就改回直连。

pion 4.4 也带有自动续提名（renomination），能不重启就换线路，但要求两端都开启，对端是旧版本时不起作用。ICE 重启是标准做法；对端是 1.1.0 时，按代码逻辑也能配合：它会把重启的 offer 当成新握手，状态短暂显示「连接中」，随后照常恢复。这一点没有单独测试，两台都升级最稳妥。

### 9. 发现失效的连接，补发没送达的内容（1.1.1）

**问题。**1.1.1 开发期间又遇到一次：家里那台断线后，本端一直以为连接还在，此后复制的 6 个文件全部「发」进了一条死连接，对方一个也没收到，日志却记着「内容已发送」。三处缺陷叠在一起：

1. pion 报告连接「失败」或「已关闭」后，本端只把状态改成离线，没有关闭连接。`Connect` 看到连接对象还在就直接返回，重连巡检因此永远重连不上。
2. 控制通道在连接失败后仍显示「打开」，消息照样写进去，发送不报错。
3. 推送文件时，等发送缓冲排空的 60 秒超时到了也按成功处理。

**做法。**

- 连接进入「失败」或「已关闭」就关闭清理，交给重连巡检重建。本端主动关闭、或已被新连接替换的旧连接发来的迟到状态一律忽略，不影响新连接。
- 对端重建了连接（例如重启了后台服务）时，它发来的 offer 带着新的 DTLS 证书。本端发现指纹变了就丢弃旧连接、新建一个应答，不在旧连接上协商到超时。
- 连接不在直连/中转状态时，发送一律返回「未连接」。缓冲排不空按失败处理。
- **补发**：同步引擎不再「广播一次了事」，而是逐台设备发送。没送达的（连不上、推送中途断开）记进该设备的待补发队列，连接建立或恢复时补发。队列在内存里，每台设备最多 20 条、24 小时内的；已删除的记录跳过。补发的 offer 带 `backlog` 标记，对端只记进复制记录，不写进剪贴板：对方此刻剪贴板里的内容比这些旧内容更新。

### 10. 谁先发包（1.1.2）

**问题。**1.1.1 装上之后，本机重启时 1～3 秒就直连；家里那台一重启，就落到中转，之后几次 ICE 重启也换不回直连：

```
00:28:00.185  P2P 连接状态  connecting   家里那台刚重启上线
00:28:05.947  P2P 连接状态  relay
00:28:15.947  当前经中转，尝试换成直连  attempt=1
00:28:51.411  当前经中转，尝试换成直连  attempt=2
00:30:16.195  信令已连接                 本机重启
00:30:17.363  P2P 连接状态  direct
```

临时打开 pion 的 ICE 日志对比成功的那次：本机往家里那台的地址发出第一个包，65 毫秒后才收到对方的第一个包，本机先发。失败的几次正好相反：

- 家里那台刚重启时，本机的出口地址早已探测好，随 offer 一起发过去；对方一收到就开始往这些地址发包。本机要等对方的 answer 和出口地址经服务器绕回来，才能往对方发包，晚了一个信令来回。
- ICE 重启也是这个顺序：本机发出重启的 offer 和出口地址，对方先发包。
- 本机重启时，出口要现探测（几百毫秒），出口地址晚于 offer 发出，本机反而先发包，所以总能直连。

**根因。**谁的包先到，谁的路由器就先收到一个「陌生来源」的包。公司路由器没有丢弃它，而是留下了一条连接记录，占住了「出口地址:端口 ↔ 对方地址:端口」这一对。本机随后往同一个对方地址发包时，源端口与这条记录冲突，路由器只好换一个端口；事先告诉对方的地址就对不上了，对方的包也一直撞在那条记录上。这条记录要在对方停止发包 30 秒左右后才过期，而每次重启对方又先发包，于是一直打不通。家里的路由器（运营商级 NAT）直接丢弃这类包，不受影响。

NAT 实验室起初没有复现，是因为模拟路由器都丢弃外来的新连接（第六节「踩过的坑」里那条），而且实验室里信令没有延迟，两端几乎同时发包。去掉公司侧路由器的丢弃规则、给信令加上 80 毫秒延迟后，旧代码稳定落到中转，后续的重启也都失败；连探测服务器看到的公网端口都被挤得变了，与实测公司网络里出口 C、D 端口忽变的现象一致。

**做法。**让「先发包」由规则决定，而不是靠运气：

- 等待的一方先不公布出口地址，等收到对方本轮的出口地址、本端发往那里的包已经发出（再留 200 毫秒），才公布自己的。这样本端的路由器先有一条本端发起的记录，对方的包回来正好对上；先收到陌生包的是对方的路由器。最多等 3 秒，对方是没有出口地址的旧版本时照常发出。
- 初次握手由发起方等。用户这一对设备里发起方恰好是公司那台，初次握手就能打通。
- 若先收到包的那一侧路由器才是会占端口的，初次握手会失败。所以换直连的重试里两种顺序轮流用：第一次重试请应答方等（`SdpOffer.answerer_waits`），第二次换回发起方等，依此类推。哪一侧的路由器有这个毛病，最多一次重试就能避开；两侧都有就只能中转。
- 「出口地址」靠格式识别：出口探测生成的 srflx candidate 不带 ufrag 扩展，pion 自己收集的都带。

## 四、能覆盖哪些场景

| 本端 | 对端 | 结果 |
|---|---|---|
| 单出口 | 单出口 | 直连 |
| 多出口（按目标 IP 选） | 单出口 | 直连 |
| 多出口 | 多出口 | 直连（实验室验证；能否成立取决于两边线路组合，属于尽力而为） |
| 任意 | 端口随机分配的 NAT | 中转 |
| 任意 | UDP 被拦截 | 中转 |
| 同一局域网 | — | 直连 |

只要多出口的一侧升级，就能与旧版本的对端直连：新增的只是标准的 srflx candidate，旧版本照常处理。

## 五、验证

### 单元测试与集成测试

`p2p/egress_test.go`：解析服务器地址；过滤污染地址；同一出口被多台服务器看到时归并；区分改写端口与不改写端口；按历史补出口、换网络不串用、过期失效；生成的 candidate 能被 pion 解析，且实测地址优先级高于推算地址。

`p2p/egress_integration_test.go`：起一台本机 STUN 服务，验证管理器在共享端口上完成探测，把出口地址作为 srflx candidate 发给对端，连接照常建立。

### NAT 打洞实验室

`tools/natlab/run.sh` 用 Linux 网络命名空间与 iptables 搭出真实拓扑，`client-core/cmd/natlab` 用隔空贴真实的 P2P 代码扮演两台设备：

```
[a] 192.168.10.2 ── [rA] 出口 10.255.0.11–14 ──┐
                                               [inet] 信令  TURN  STUN×4
[b] 192.168.20.2 ── [rB] 出口 10.254.0.21–22 ──┘
```

rA 用 SNAT 规则按目标地址选出口，还原公司网络；rB 还原家用路由器或端口随机分配的 NAT。两台路由器都丢弃外网主动发起的新连接，与真实路由器一致（原因见「踩过的坑」）。

| 场景 | 预期 | 结果 |
|---|---|---|
| 单出口 ↔ 家用路由器 | 直连 | 通过 |
| 两个出口，旧版本（对照） | 中转 | 通过：复现了原问题 |
| 两个出口 ↔ 家用路由器 | 直连 | 通过 |
| 四个出口 ↔ 家用路由器 | 直连 | 通过 |
| 两个出口，第二条没探测到，无历史 | 中转 | 通过 |
| 两个出口，第二条没探测到，有历史 | 直连 | 通过 |
| 两个出口 ↔ 两个出口 | 直连 | 通过 |
| 两个出口 ↔ 端口随机分配的 NAT | 中转 | 通过 |
| 一开始打不通，8 秒后网络恢复（1.1.1） | 先中转，随后换成直连 | 通过 |
| 公司路由器会为外来的包占住端口，信令延迟 80 毫秒（1.1.2） | 直连（初次握手即打通） | 通过；1.1.1 在这里落到中转，重试也失败 |
| 家用路由器会为外来的包占住端口，信令延迟 80 毫秒（1.1.2） | 先中转，第一次重试换对方先发包后直连 | 通过 |

最后一个场景让家用路由器开头 8 秒不放行发往公司出口的 UDP，第一次握手只能落到中转；放开后，脚本还要求日志里确实出现了「中转 → 尝试换成直连」，排除一开始就碰巧直连的情况。

本地运行：`./tools/natlab/docker.sh`（macOS 上在特权容器里跑；国内网络加 `APK_MIRROR=mirrors.aliyun.com`）。CI 的 `natlab` 任务在每次提交时运行。

## 六、踩过的坑

- **pion 为每台 STUN 服务器单独开端口。**这是多配 STUN 服务器也打不通的原因，也是改用共享端口的出发点。
- **单靠本端判断「是否中转」会出错。**一端经 TURN 发送时，另一端看到的源地址可能是 peer-reflexive 地址，并不标为 relay。这曾导致两台设备一台显示直连、一台显示中转，靠两端交换 `LinkInfo` 解决。
- **实验室路由器必须丢弃外网主动发起的新连接。**两端同时打洞时，对方的包可能先到达本端路由器。若放行到路由器本机，Linux conntrack 会为它建一条「未应答」记录；随后本端往外发时源端口与之冲突，SNAT 只好换一个端口，事先告诉对端的地址就失效了。真实路由器的防火墙直接丢弃这类包，被丢弃的包不会留下连接记录。没加这条规则时，连最简单的单出口场景都会误判为打不通。
- **公共 STUN 域名可能被污染。**`stun.syncthing.net` 在测试网络里被解析到 `192.0.2.42`。不过滤的话，要么白等超时，要么被当成一个出口。
- **实验室场景要互相隔离。**出口历史文件跨场景残留，曾让「无历史」场景意外直连。这反过来也说明历史推算确实生效。
- **pion 选定 candidate 对后不再更换。**一次握手输给中转，整个连接期间都是中转。等待时限只能降低输的概率，要补救得靠 ICE 重启（第 8 节）。
- **模拟路由器太「规矩」会掩盖问题。**实验室里的路由器都丢弃外来的新连接、信令又没有延迟，于是「谁先发包」从来不是问题；真实的公司路由器会为外来包占住端口，信令也要绕服务器几十毫秒。现在实验室两种路由器都有，会占端口的场景给信令加了延迟。
- **pion 报告失败后不会自己关闭连接**，控制通道也仍显示打开。只把状态改成离线是不够的，必须关闭清理，否则上层永远不会重连（第 9 节）。

## 七、局限与后续

- **对端是端口随机分配的 NAT 时仍会中转。**理论上可以做端口预测或大规模并发打洞，但成功率低、流量大，暂不做。
- **UDP 被拦截时只能中转。**后续可以增加 TURN over TCP/TLS（443 端口）。
- **探测覆盖取决于服务器 IP 的分散程度。**线路越多，越需要更多 IP。服务器可以用 `-stun` 参数下发更多 STUN 地址，客户端会一并探测。
- **待补发队列只在内存里。**本机后台服务重启后清空；对方离线超过 24 小时的内容也不补发。
- **两边都有公网 IPv6 时最省事。**pion 会直接收集 IPv6 地址，无需穿越 NAT。这次的两台设备都没有。
